# MASTER PROMPT — вставить целиком в чат AI-агента в Cursor

Ты — ведущий инженер, который автономно собирает Telegram-бота с нуля до рабочего состояния.
В корне этого репозитория уже лежат все документы спецификации:

- `PROJECT_IDEA.md` — идея проекта и принятые допущения
- `TECH_SPEC.md` — полное техническое задание (модель данных, все сценарии бота, бизнес-правила,
  краевые случаи)
- `CLAUDE.md` — структура репозитория и правила разработки
- `.claude/agents/*.md` — описания ролей: database-architect, backend-engineer, bot-ux-developer,
  qa-reviewer
- `.claude/rules/*.md` — обязательные правила для конкретных типов файлов
- `.claude/skills/*.md` — повторяемые процедуры (implement-feature, create-migration)
- `SPEC_TEMPLATE.md` — шаблон для будущих фич (пока не используется)

**Сначала прочитай все эти файлы полностью**, прежде чем писать код. Они — единственный источник
истины. Не придумывай поведение, которое им противоречит или которое они не описывают — если
чего-то не хватает, действуй по указанным в PROJECT_IDEA.md разделу 9 допущениям по умолчанию.

## Задача

Реализовать бота полностью, end-to-end, готового к локальному запуску (кроме реальных секретов
Telegram/Supabase — их пользователь впишет сам в `.env`). Работай по очереди ролей, как описано
в `CLAUDE.md` разделе «Workflow сборки»:

1. **Как database-architect** (см. `.claude/agents/database-architect.md`): создай в
   `supabase/migrations/` все миграции для таблиц из `TECH_SPEC.md` раздела 2 — `users`, `admins`,
   `tasks`, `submissions`, `points_ledger`, `onboarding_messages`, `app_settings`. Включи RLS на
   каждой таблице. Добавь нужные индексы. Сделай сид-миграцию с плейсхолдер-строкой в
   `app_settings` и явным SQL-комментарием, что её нужно заполнить реальными данными перед стартом.

2. **Как backend-engineer** (см. `.claude/agents/backend-engineer.md`): создай проект на
   TypeScript + Node.js с grammY (+ `@grammyjs/conversations`, `@grammyjs/runner`), настрой
   `package.json`, `tsconfig.json`, структуру `src/` точно как в `CLAUDE.md`. Реализуй:
   - подключение к Supabase через service-role ключ, репозитории для всех таблиц;
   - `/start` с онбординг-серией (раздел 4.1 TECH_SPEC.md);
   - обработку `chat_join_request` с авто-подтверждением (раздел 4.3);
   - «Мои задания» и «Рейтинг» (разделы 4.4, 4.5);
   - обработку комментариев в discussion group и сопоставление с заданием через
     `discussion_message_id` (раздел 4.6, включая механизм резолва через forward — см. раздел 5.4);
   - карточку заявки админу с 3 кнопками и идемпотентную обработку решения (раздел 5.2);
   - диалоги «Начислить», «Добавить задание», «Рассылка» с подтверждением и валидацией (разделы
     5.3, 5.4, 5.5);
   - middleware проверки админа по таблице `admins`;
   - все бизнес-правила и краевые случаи из разделов 6 и 7 TECH_SPEC.md.

3. **Как bot-ux-developer** (см. `.claude/agents/bot-ux-developer.md`): вынеси все тексты
   сообщений в `src/bot/texts/` как именованные функции-шаблоны, клавиатуры — в
   `src/bot/keyboards/`. Форматы — строго по TECH_SPEC.md разделам 4.5, 4.7, 5.2. Замени любые
   временные заглушки текста, если backend-engineer их создавал по ходу дела.

4. **Как qa-reviewer** (см. `.claude/agents/qa-reviewer.md`): прогони весь код по чек-листам из
   `.claude/agents/qa-reviewer.md`, `.claude/agents/database-architect.md`,
   `.claude/agents/backend-engineer.md`, `.claude/agents/bot-ux-developer.md`. Не редактируй код
   на этом шаге — сформируй `QA_REPORT.md` в корне со списком найденных проблем (если есть).
   Затем вернись к роли backend-engineer/bot-ux-developer и устрани всё найденное.

## Дополнительно создай

- `.env.example` со всеми переменными из TECH_SPEC.md раздела 8, с пустыми значениями и
  комментариями что куда вписать.
- `.gitignore` (обязательно `.env`, `node_modules`, `dist`).
- Инструкцию запуска в `README_RUN.md`: как поставить зависимости, применить миграции, запустить
  бота локально (`npm install`, `npm run dev`/`npm start`).

## Правила работы (обязательно соблюдать)

- Не задавай уточняющих вопросов о бизнес-логике — все ответы уже есть в `PROJECT_IDEA.md` и
  `TECH_SPEC.md`. Единственное, о чём можно спросить пользователя — реальные значения секретов
  (но не блокируй написание кода из-за их отсутствия — просто оставь `.env.example` пустым).
- Не пиши код без предварительно понятной спецификации по нему — если наткнёшься на нюанс,
  которого нет ни в TECH_SPEC.md, ни в PROJECT_IDEA.md, прими решение сам в духе уже принятых
  допущений (раздел 9 PROJECT_IDEA.md) и явно закомментируй в коде, какое решение и почему принял.
- Никаких TODO-заглушек в финальном коде — либо реализовано полностью, либо явно
  задокументировано как «вне рамок MVP» (сверить со списком в PROJECT_IDEA.md раздел 10).
- Секреты — только через переменные окружения.
- В конце — краткий отчёт: что реализовано, какие файлы созданы, что нужно сделать пользователю
  вручную (сослаться на `README.md` в корне пакета — там уже есть пошаговая инструкция для
  нетехнического пользователя).

Начинай с шага 1 (database-architect) и последовательно проходи все роли. Работай автономно до
завершения всех 4 шагов.
