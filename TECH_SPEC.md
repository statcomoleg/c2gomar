# TECH_SPEC — Telegram-бот марафона «Контент-завод»

Источник: PROJECT_IDEA.md. Этот документ — техническое задание для AI-агентов. Всё, что здесь
написано, реализуется без уточняющих вопросов и без TODO-заглушек.

---

## 1. Стек

- Язык: **TypeScript** (Node.js 20+)
- Bot-фреймворк: **grammY** (+ плагин `@grammyjs/conversations` для многошаговых диалогов админа,
  + плагин `@grammyjs/runner` для устойчивого long polling)
- База данных: **Supabase (Postgres)**, доступ через `@supabase/supabase-js` с service-role ключом
- Хостинг: Node-процесс на Railway/Render (long polling, `npm start` запускает один процесс)
- Валидация: `zod` для всех входных данных от админ-диалогов
- Даты/время: `date-fns` (таймзона МСК по умолчанию, см. env `TZ`)

## 2. Модель данных (Supabase / Postgres)

```sql
-- users: все, кто хоть раз написал боту /start
create table users (
  id bigint primary key,                 -- telegram user id
  username text,
  first_name text,
  joined_channel_at timestamptz,         -- null пока не вступил в канал
  total_points integer not null default 0,
  last_points_at timestamptz,            -- когда в последний раз менялись баллы (для тай-брейка рейтинга)
  onboarding_step integer not null default 0,
  created_at timestamptz not null default now()
);

-- admins: telegram id админов (дублирует env ADMIN_TELEGRAM_IDS для удобства запросов из БД)
create table admins (
  id bigint primary key,
  added_at timestamptz not null default now()
);

-- tasks: ПДЗ и ДЗ, заведённые админом
create table tasks (
  id serial primary key,
  type text not null check (type in ('pre', 'main')),  -- pre = ПДЗ, main = ДЗ
  label text not null,                    -- "ПДЗ 1", "ДЗ 3" — генерируется автоматически по порядку в типе
  description text not null,              -- краткое описание, вводит админ
  channel_post_link text not null,        -- ссылка вида https://t.me/c/.../123 или https://t.me/channelname/123
  channel_message_id bigint not null,     -- распарсенный id поста в канале
  discussion_message_id bigint,           -- id пересланной копии в группе обсуждений (заполняется автоматически)
  is_active boolean not null default true,
  created_by bigint references admins(id),
  created_at timestamptz not null default now()
);
create unique index tasks_channel_message_id_idx on tasks(channel_message_id);

-- submissions: отчёты пользователей (комментарии) по заданиям
create table submissions (
  id serial primary key,
  task_id integer not null references tasks(id),
  user_id bigint not null references users(id),
  comment_message_id bigint not null,     -- id сообщения-комментария в группе обсуждений
  comment_text text not null,
  status text not null default 'pending'
    check (status in ('pending', 'approved', 'rejected', 'superseded')),
  points_awarded integer,
  reviewed_by bigint references admins(id),
  reviewed_at timestamptz,
  submitted_at timestamptz not null default now()
);
create index submissions_task_user_idx on submissions(task_id, user_id);

-- points_ledger: журнал начислений (аудит + источник для рейтинга/тай-брейка)
create table points_ledger (
  id serial primary key,
  user_id bigint not null references users(id),
  points integer not null,                -- может быть отрицательным при ручной корректировке
  reason text not null,                    -- 'task_approved' | 'manual'
  related_submission_id integer references submissions(id),
  related_task_id integer references tasks(id),
  admin_id bigint references admins(id),
  created_at timestamptz not null default now()
);

-- onboarding_messages: серия сообщений для новых пользователей (тексты добавляет админ позже)
create table onboarding_messages (
  id serial primary key,
  step_order integer not null unique,
  text text not null,
  delay_seconds integer not null default 0,  -- задержка перед отправкой ОТНОСИТЕЛЬНО предыдущего шага
  created_at timestamptz not null default now()
);

-- app_settings: единственная строка с общими настройками марафона
create table app_settings (
  id boolean primary key default true check (id),  -- singleton-паттерн, всегда одна строка
  marathon_start_at timestamptz not null,
  channel_id bigint not null,
  discussion_group_id bigint not null
);
```

RLS: включить на всех таблицах (`enable row level security`), политик для anon/authenticated
НЕ создавать — единственный клиент базы это сам бот через service-role ключ, который RLS обходит.
RLS включён как defense-in-depth на случай утечки anon-ключа в будущем (например, если появится
веб-панель).

## 3. User Stories

1. Как **новый пользователь**, я хочу написать `/start` боту и получить серию вовлекающих
   сообщений, чтобы понять суть марафона и захотеть в нём участвовать.
2. Как **пользователь**, я хочу получить кнопку/ссылку на закрытый канал и, подав заявку,
   автоматически быть принятым, чтобы не ждать ручного одобрения.
3. Как **участник**, я хочу написать отчёт о выполнении задания комментарием под постом в канале,
   чтобы не искать отдельную форму или чат.
4. Как **участник**, я хочу получить уведомление в боте, когда моё задание одобрено (с указанием
   начисленных баллов) или отправлено на доработку (с понятной причиной — что доработать).
5. Как **участник**, я хочу нажать «Мои задания» и увидеть список всех опубликованных заданий с
   отметкой, что уже выполнено, а что нет, и по клику — статус и ссылку на пост.
6. Как **участник**, я хочу нажать «Рейтинг» и увидеть топ-10 по баллам, а также своё место и
   баллы, даже если я не в топ-10.
7. Как **админ**, я хочу завести задание (ПДЗ или ДЗ) с описанием и ссылкой на пост одним диалогом,
   чтобы бот сам начал отслеживать комментарии под этим постом.
8. Как **админ**, я хочу получать карточку с текстом отчёта пользователя и тремя кнопками
   (доработка / +3 / +10), чтобы проверять задания в одно касание.
9. Как **админ**, я хочу вручную начислить баллы конкретному пользователю с подтверждением,
   чтобы поощрить активность вне формальных заданий.
10. Как **админ**, я хочу сделать рассылку с текстом и картинкой всем пользователям или только тем,
    у кого рейтинг выше/ниже порога, чтобы точечно мотивировать аудиторию.

## 4. Сценарии бота (handlers) — Участник

### 4.1 `/start`
- Если пользователь новый — создать запись в `users`, начать онбординг-серию: отправлять шаги из
  `onboarding_messages` по порядку `step_order` с паузой `delay_seconds` между ними (через
  `setTimeout`/очередь, не блокируя обработку других апдейтов).
- Если пользователь уже существует — показать главное меню (см. 4.2) без повторного онбординга.
- Финальный шаг онбординга обязательно включает кнопку/ссылку-приглашение в закрытый канал
  (invite link с `creates_join_request = true`).

### 4.2 Главное меню участника (reply-клавиатура или inline, после онбординга/при `/menu`)
- Кнопка **«Мои задания»**
- Кнопка **«Рейтинг»**

### 4.3 `chat_join_request` (заявка на вступление в канал)
- Бот автоматически подтверждает заявку (`approveChatJoinRequest`), если запрос пришёл от chat_id
  канала из `app_settings.channel_id`.
- Обновить `users.joined_channel_at = now()`.
- Отправить пользователю приветственное сообщение в боте: канал открыт, где искать задания.

### 4.4 «Мои задания»
- Запросить все `tasks` где `is_active = true`, отсортировать: сначала `type='pre'` по `label`,
  затем `type='main'` по `label`.
- Для каждого задания — inline-кнопка с текстом `✅ {label}` если у пользователя есть submission
  со `status='approved'` по этому task_id, иначе `▫️ {label}`.
- Если заданий нет вообще — сообщение «Пока нет доступных заданий, следите за постами в канале».
- По клику на кнопку конкретного задания — показать: описание, ссылку на пост (`channel_post_link`),
  статус для этого пользователя (Не начато / На проверке / Одобрено, +N баллов / Отправлено на
  доработку — с текстом последнего комментария от админа, если был).

### 4.5 «Рейтинг»
- Топ-10 пользователей по `total_points` desc, при равенстве — по `last_points_at` asc (раньше
  достиг суммы — выше).
- Формат сообщения:
  ```
  🏆 Рейтинг марафона

  Ваше место: #{N} — {points} баллов

  1. {username1} — {points1}
  2. {username2} — {points2}
  ...
  10. {username10} — {points10}
  ```
- Если пользователь не в топ-10, его место всё равно вычисляется полным запросом ранжирования
  (`row_number() over (order by total_points desc, last_points_at asc)`).
- Если у пользователя `username` не задан — показывать `first_name`.

### 4.6 Новый комментарий в discussion group (обработка отчётов)
Триггер: любое новое сообщение в chat_id из `app_settings.discussion_group_id`, у которого есть
`reply_to_message`.

Шаги:
1. Определить `discussion_message_id` = `reply_to_message.message_id` (либо, если это ответ внутри
   треда на другой комментарий — подняться по цепочке `reply_to_message` до сообщения, являющегося
   форвардом из канала, чтобы найти корневой пост).
2. Найти `tasks` где `discussion_message_id` совпадает. Если не найдено — игнорировать сообщение
   (это не отчёт по известному заданию).
3. Если найдено и `task.type = 'pre'` и `now() > app_settings.marathon_start_at` — отправить
   пользователю сообщение «Приём предварительных заданий завершён, этот тип заданий больше не
   засчитывается» и не создавать submission.
4. Если найдено и `task.type = 'main'` и `now() < app_settings.marathon_start_at` — аналогично
   отклонить с сообщением «Основные задания открываются после старта марафона {дата}».
5. Иначе — создать `submissions` со `status='pending'`, `comment_text` = текст сообщения,
   `comment_message_id`. Если у пользователя уже есть `pending`/`approved` submission по этому же
   `task_id` — если `approved`, ответить пользователю «Это задание уже одобрено ✅», submission не
   создавать; если `pending` — создать новый и пометить предыдущий как `superseded` (пользователь
   мог доотправить исправленный текст, не дожидаясь реакции админа).
6. Разослать карточку заявки всем `admins` (см. раздел 5.2).

### 4.7 Уведомление об одобрении/доработке (сообщение пользователю)
- Одобрено: `✅ Задание {label} принято! Начислено +{points} баллов. Ваш баланс: {total_points}.`
- Доработка: `🔁 Задание {label} отправлено на доработку. Проверьте комментарии куратора и пришлите исправленный отчёт под тем же постом.`

## 5. Сценарии бота (handlers) — Админ

Доступ ко всем админ-функциям — только если `ctx.from.id` есть в таблице `admins` (проверка в
middleware, для остальных — просто игнорировать команду/кнопку без утечки информации о её наличии).

### 5.1 Главное меню админа (по `/admin`)
- Кнопка **«Начислить»**
- Кнопка **«Добавить задание»**
- Кнопка **«Рассылка»**

### 5.2 Карточка новой заявки на проверку (админу, в личку боту)
Отправляется всем админам при создании новой `submission` (шаг 4.6.6):
```
📝 Новый отчёт
Задание: {task.label} — {task.description}
От: @{username} ({first_name})
Текст:
{comment_text}
```
Inline-кнопки: `🔁 На доработку` | `+3 балла` | `+10 баллов`

Логика при нажатии (любым из админов — первый нажавший забирает заявку):
- Обновить `submissions.status`, `reviewed_by`, `reviewed_at`.
- Если approve — записать `points_ledger` (points = 3 или 10, reason='task_approved'), обновить
  `users.total_points += points`, `users.last_points_at = now()`.
- Отредактировать сообщение у ВСЕХ админов (или хотя бы у нажавшего) — убрать кнопки, дописать
  `✅ Обработано: {admin_username}, решение: {результат}`, чтобы не было повторной обработки.
- Отправить пользователю уведомление (см. 4.7).

### 5.3 «Начислить»
Диалог (conversations plugin), пошагово:
1. Бот просит переслать сообщение пользователя ИЛИ ввести его Telegram ID/username.
2. Бот просит ввести количество баллов (целое число, может быть отрицательным для коррекции).
3. Бот показывает подтверждение: `Начислить {points} баллов пользователю {username} (id {id})?`
   с кнопками `Подтвердить` / `Отмена`.
4. При подтверждении — запись в `points_ledger` (reason='manual', admin_id), обновление
   `users.total_points`, `users.last_points_at`; пользователю приходит уведомление
   `💰 Вам начислено {points} баллов админом. Баланс: {total_points}.`

### 5.4 «Добавить задание»
Диалог:
1. Бот спрашивает тип: `ПДЗ` / `ДЗ` (inline-кнопки).
2. Бот просит краткое описание (текст, до 500 символов).
3. Бот просит **ссылку на пост** в канале (валидация `https://t.me/...`).
4. Бот парсит `channel_message_id` из ссылки, автоматически присваивает `label` (следующий
   порядковый номер в рамках выбранного типа: «ПДЗ 3», «ДЗ 1» и т.д.), сохраняет `tasks` со
   `discussion_message_id = null`, `is_active = true`.
5. Показывает админу подтверждение с итоговыми данными.
6. Фоновый обработчик: при автофорварде поста в discussion group (`forward_origin.type = channel`
   + `is_automatic_forward`) проставляет `discussion_message_id`. Fallback: при первом комментарии
   (reply на форвард) биндит по `forward_origin.message_id` = `channel_message_id`.

### 5.5 «Рассылка»
Диалог:
1. Бот просит ввести текст сообщения (HTML-разметка) и, опционально, прикрепить фото.
2. Бот спрашивает аудиторию: `Все` / `Рейтинг выше N` / `Рейтинг ниже N` (при выборе последних
   двух — просит ввести число N).
3. Показывает превью сообщения и количество получателей, просит подтверждение.
4. Рассылка выполняется пачками с паузой между отправками (~30–40 сообщений/сек с учётом лимитов
   Telegram), ошибки (заблокировал бота и т.п.) логируются и не прерывают рассылку.
5. По завершении — админу отчёт: `Разослано: {success}/{total}, ошибок: {failed}`.

### 5.6 «Онбординг» (редактирование цепочки)
- Список шагов из `onboarding_messages`, правка текста (HTML) и `delay_seconds` без деплоя.
- `/save_circle` или кнопка: админ присылает video note → `media_file_id` пишется в шаг с
  `media_type = video_note`.

## 6. Бизнес-правила (сводка)

- ПДЗ принимаются только до `marathon_start_at`, ДЗ — только после.
- Одна активная (`pending`/`approved`) submission на пару (user, task) — новая заявка "гасит"
  предыдущую `pending`, если предыдущая уже `approved` — новые попытки игнорируются с уведомлением.
- Баллы начисляются только через `points_ledger` (единый источник правды), `users.total_points` —
  денормализованный кэш, пересчитывается атомарно в той же транзакции, что и вставка в ledger.
- Доступ к админ-функциям — только id из таблицы `admins`.
- Рассылка никогда не блокирует основной поток обработки апдейтов (выполняется асинхронно/в фоне).

## 7. Краевые случаи

- Пользователь пишет комментарий не под известным постом → игнорируется молча (не отчёт).
- Пользователь пишет несколько раз подряд под одним постом до проверки → все лишние помечаются
  `superseded`, на проверку админу уходит только последняя версия (можно уведомить админа, что
  предыдущую карточку больше не нужно проверять — отредактировать её сообщением "заменено новым").
- Админ пытается завести задание со ссылкой на пост, который уже заведён (дубликат
  `channel_message_id`) → бот сообщает "Это задание уже существует: {label}", не создаёт дубль.
- Двое админов одновременно нажимают кнопки на одной карточке заявки → второй клик получает
  ответ "Уже обработано пользователем {admin}", изменений не происходит (проверка статуса перед
  апдейтом, идемпотентно).
- Дата старта марафона (`marathon_start_at`) не задана при первом деплое → бот при старте
  проверяет наличие строки в `app_settings`, при отсутствии — явно требует создать её (миграция
  сидом с плейсхолдер-датой, которую нужно поменять перед стартом — единственное разрешённое
  "TODO", т.к. это конфигурационные данные, а не код).
- Пользователь заблокировал бота → рассылка/уведомление ловит ошибку Telegram API, помечает
  как failed, не роняет процесс.

## 8. Переменные окружения (`.env`)

```
BOT_TOKEN=
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
ADMIN_TELEGRAM_IDS=123456789,987654321
TZ=Europe/Moscow
```

(`channel_id`, `discussion_group_id`, `marathon_start_at` — хранятся в таблице `app_settings`,
не в env, чтобы админ мог менять их без передеплоя, но начальные значения задаются один раз
вручную через прямой SQL/скрипт при первом деплое.)

## 9. Приоритет реализации (для параллельной сборки сабагентами)

1. **database-architect**: миграции всех таблиц из раздела 2 + RLS.
2. **backend-engineer**: core бот (grammY init, middleware проверки админа, все handlers из
   разделов 4 и 5, работа с Supabase).
3. **bot-ux-developer**: все тексты сообщений, форматирование клавиатур, тексты карточек — строго
   по форматам из раздела 4–5, без отсебятины в формулировках.
4. **qa-reviewer**: прогон по чек-листу раздела 7 (краевые случаи) + проверка что admin-only
   функции недоступны обычным пользователям + проверка что секреты не закоммичены в код.
